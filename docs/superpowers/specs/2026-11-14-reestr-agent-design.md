# Агент реестра исполнительной документации — проект решения

> Исторический документ: написан в ходе работы на документах реального объекта, которых в репозитории нет.
> Номера актов, объёмы и названия обезличены; счётчики вроде «63 акта» относятся к тем документам,
> а не к синтетическим примерам из `examples/`.

Дата: 2026-11-14. Статус: на согласовании.

## Зачем

Инженер подрядчика на строительстве автодороги вручную переносит данные из актов
освидетельствования скрытых работ (АОСР) в реестр исполнительной документации. Актов сотни, работа
механическая. Нужен помощник в Telegram: инженер кидает акты, получает обновлённый реестр, а спорные
места помощник уточняет у него сам.

Второй мотив — владелец проекта (Алексей) хочет попробовать pi как основу для агента и получить
заготовку, на которую потом можно навешивать другие сценарии работы со строительными документами.

## Цели

1. Принять акты в двух форматах и разобрать их в одну и ту же структуру:
   - книга xlsx, один лист — один акт (редактируемый формат);
   - скан PDF без текстового слоя: первые 2 страницы — акт, дальше приложения (их может не быть).
2. Вести один накопительный реестр (лист «общий» шаблона инженера): дозапись, сортировка по дате акта,
   без дублей, с сохранением колонок, которые инженер заполняет руками.
3. Диалог в Telegram: агент сам задаёт вопросы по спорным местам, выполняет команды словами
   (поправить поле, удалить акт, отменить последнее изменение) и отвечает на вопросы по реестру.
4. Архитектура, в которую новый сценарий добавляется как новый инструмент, без переделки остального.

## Не цели (сейчас)

- Другие типы документов (акты ответственных конструкций, акты разбивки осей и т. п.).
- Несколько реестров, несколько объектов, несколько пользователей с разными правами.
- Анонимизация данных перед отправкой в модель (будет позже; вызов модели делаем в одном месте).
- Заполнение колонок № КС, № п/п, период «с — по», организация, «Реестр №» — инженер ведёт их сам.
- Веб-интерфейс.

## Чего быть не должно (анти-цели)

- Модель не пишет в ячейки реестра напрямую и не решает, как обрабатывать файл. Один и тот же акт
  всегда даёт одну и ту же строку.
- Агент не получает командную строку и доступ к файлам: только наши инструменты.
- Молчаливых догадок в реестре: всё, что распознано неуверенно, либо уточняется у инженера, либо
  попадает в реестр с явной пометкой в отчёте.
- Удаление и перезапись данных без подтверждения кнопкой.

## Ограничения

- Модели — только через хаб neuraldeep (`https://api.neuraldeep.ru/v1`, OpenAI-совместимый). Для актов
  используем модели на своих GPU в РФ: `qwen3.6-fp8`, `qwen3.8-27b` (обе принимают изображения).
- Пользователь один (инженер), плюс Алексей для отладки. Доступ по списку Telegram-id.
- Правила заполнения реестра согласованы с инженером 14.11.2026 (см. «Правила реестра»).
- pi — пакет `@earendil-works/pi-coding-agent` (Node/TypeScript), API меняется между версиями: версию
  фиксируем.

## Рассмотренные варианты

1. **Бот без агента** — фиксированные кнопки. Предсказуемо, но уточнения и команды только заранее
   предусмотренные. Отклонён: не даёт диалога и расширяемости.
2. **Агент ведёт всё** — каждый файл проходит через цикл агента. Отклонён: результат обработки зависит
   от модели, а реестр уходит заказчику.
3. **Конвейер + агент на диалоге** — выбран Алексеем. Файлы всегда идут одним детерминированным путём,
   агент ведёт разговор и вызывает инструменты ядра.

Основа агента: **pi** (выбор Алексея — хочет попробовать). Альтернатива — свой цикл вызова
инструментов на Python — остаётся запасным путём, если проба pi с локальной моделью провалится.

## Устройство

```
Telegram ──► Бот (Node, grammY)
               │  файл                         │  текст / нажатие кнопки
               ▼                               ▼
        Конвейер (вызов ядра,           Агент (pi SDK, сессия на чат,
        без участия модели-агента)      встроенные инструменты выключены)
               │  итог + спорные места         │  вызовы инструментов
               └──────────► сообщение агенту ◄─┘
                                   │
                                   ▼
                     Ядро (Python, команды с ответом в JSON)
                     разбор xlsx · разбор сканов · операции с реестром
                                   │
                                   ▼
                 Рабочая папка: реестр.xlsx · история версий ·
                 входящие файлы · открытые вопросы
```

### Ядро (Python)

Детерминированная библиотека и набор команд `aosr <команда>` с ответом в JSON. За основу берётся
черновик, собранный 14.11 (модель акта, разбор xlsx, запись реестра, 11 тестов); он дорабатывается под
этот проект.

Команды:

| Команда | Что делает |
|---|---|
| `ingest <файлы>` | разобрать акты (xlsx, pdf), внести в реестр, вернуть итог и спорные места |
| `list` / `find` | перечень актов с отбором по номеру, дате, тексту |
| `show <номер>` | один акт целиком |
| `set <номер> <поле> <значение>` | исправить поле акта |
| `delete <номер>` | удалить акт с приложениями |
| `resolve <вопрос> <ответ>` | закрыть спорное место выбранным значением |
| `undo` | вернуть предыдущую версию реестра |
| `replace-registry <файл>` | принять реестр, который инженер правил у себя, как текущий |
| `export` | путь к актуальному файлу реестра |

Реестр-файл — источник правды. Каждое изменение сначала сохраняет предыдущую версию в историю
(отсюда `undo`). Колонки, которые ведёт инженер, при любых операциях сохраняются.

**Чужие строки не теряются.** В листе могут оказаться документы, которые бот не создавал (другие типы
актов, журналы). Любая непустая строка сохраняется как есть: строка с номером документа — отдельный
блок, строки без номера остаются привязанными к блоку над ними. Остатки старых данных шаблона
вычищаются один раз, при создании реестра из шаблона, а не при каждой записи.

**Ручные исправления живут дольше повторной загрузки.** Исправление через `set` и ответ на спорное
место через `resolve` запоминаются как правка «номер акта + поле → значение» и накладываются заново,
когда тот же акт приходит снова (инженер будет слать накопительную книгу целиком). Отменить правку
можно явно.

**Спорные места не задерживают акт.** Акт попадает в реестр сразу, со значением основной модели в
спорном поле, а вопрос остаётся открытым. Пока есть открытые вопросы, бот при каждой выдаче реестра
пишет, сколько их и по каким актам. `undo` возвращает и реестр, и список открытых вопросов.

**Файл реестра от инженера.** Бот отличает реестр от книги с актами по содержимому (лист «общий» с
шапкой таблицы). Присланный реестр после подтверждения становится текущим целиком. Перед заменой
бот сверяет номера: если в текущем реестре есть акты, которых нет в присланном файле, он спрашивает,
добавить их или считать удалёнными, — так не теряются акты, внесённые после того, как инженер скачал
свою копию.

### Правила реестра (согласованы с инженером)

- Строка акта: № по ведомости, «Акт освидетельствования скрытых работ», названия работ, дата, номер,
  единица, количество, место. Под ней — по строке на каждое приложение.
- Несколько работ в одном акте пишутся в одну ячейку через перенос строки (как в его примере).
- Количество и единица — из акта. Работы без номера по ведомости — колонка пустая.
- Место освидетельствования — часть названия работ после «на участке / на участках».
- Порядок — по дате акта. Дубль определяется по номеру акта; повторная загрузка обновляет строку.
- Остальные колонки не заполняются.

Открытый вопрос к инженеру (не блокирует): у 22 из 63 актов в названии нет «на участке»
(«Устройство колодцев 11-15»). Сейчас берётся часть после слова «колодцев» с пометкой в отчёте.

### Разбор сканов

1. PDF → изображения первых двух страниц (200 dpi).
2. Две разные модели со зрением (`qwen3.6-fp8` и `qwen3.8-27b`, режим без рассуждений) независимо
   возвращают поля акта в JSON по одной схеме.
3. Ответы проверяются по схеме и сравниваются по полям после нормализации (пробелы, кавычки, ё/е,
   регистр, пробелы вокруг знаков). Совпало — поле принято. Разошлось — поле становится спорным
   местом. Основная модель — `qwen3.6-fp8`: её значение идёт в реестр до ответа инженера.
   - Короткие поля (номер, даты, коды, количество, единица) — вопрос с двумя вариантами на кнопках.
   - Длинные поля (названия работ, строки приложений) — в вопросе показывается только расходящийся
     фрагмент с соседними словами, варианты «1 / 2 / напишу сам». Расхождения по приложениям одного
     акта собираются в одно сообщение, чтобы не засыпать вопросами.
4. Дальше акт идёт тем же путём, что и акт из xlsx.

Почему две модели: уверенности в ответе модели не сообщают. На образце инженера обе верно прочли
номер, даты, коды и объёмы, а разошлись ровно там, где ошиблись (номера протоколов в приложениях).
Совпадение ошибок возможно, поэтому отчёт всегда помечает акт как «из скана».

Допущения по сканам (со слов инженера): один PDF — один акт, акт занимает первые две страницы,
рукописных правок нет. Защита от нарушения: модель дополнительно возвращает, есть ли на этих
страницах блок подписей; если нет — акт помечается «возможно, не весь акт на первых двух страницах».

Ограничение Telegram: бот через обычный Bot API скачивает файлы до 20 МБ (образец — 10,5 МБ на 18
страниц). Файл больше бот не примет и попросит прислать первые страницы или сжатый скан. Если такие
файлы окажутся частыми — отдельное решение (локальный сервер Bot API), в этот проект не входит.

Материалы пробы 14.11 (подсказка, ответы четырёх моделей) лежат в `spikes/2026-11-14-vision/`.

Если акт с тем же номером уже есть в реестре и поля отличаются — это тоже спорное место
(«заменить / оставить»), а не тихая перезапись. Для xlsx-актов повтор обновляет строку без вопроса.

### Бот (Node, grammY)

- Принимает файлы и текст только от разрешённых Telegram-id.
- Файл: сохраняет во входящие, сам вызывает `aosr ingest`, результат отдаёт агенту как служебное
  сообщение («обработано то-то, спорные места такие-то»). Агент формулирует ответ и вопросы.
  После изменения реестра бот прикладывает актуальный файл.
- Текст: передаёт агенту.
- Подтверждения: удаление, замена при конфликте и `replace-registry` выполняются только после
  нажатия кнопки. Это делает код бота, а не модель: инструмент возвращает «ждёт подтверждения»,
  бот показывает кнопки и по нажатию вызывает ядро.
- Спорные места с вариантами показываются кнопками; свободный ответ текстом тоже принимается.

### Агент (pi SDK)

- Одна постоянная сессия на чат; встроенные инструменты pi (bash, read, write, edit) выключены,
  автопоиск расширений и навыков в рабочей папке отключён.
- Свои инструменты — тонкие обёртки над командами ядра: `найти_акты`, `показать_акт`,
  `исправить_поле`, `удалить_акт`, `закрыть_вопрос`, `отменить`, `сводка_реестра`, `прислать_реестр`.
- Модель диалога: `qwen3.8-27b` через хаб (подключение в `models.json`, ключ — через существующий
  `neuraldeep-hub-key`).
- Системная подсказка: роль, правила реестра, запрет выдумывать значения, обязанность спрашивать при
  сомнении, ответы короткие и по-русски.
- Текст из документов агент получает только как извлечённые поля (данные), а не как инструкции.

### Расширяемость

Новый сценарий = новая команда ядра + описание инструмента для агента. Бот и агент при этом не
меняются. Модель акта уже хранит название документа отдельным полем, так что другие типы актов
добавляются новым разборщиком.

## Проверка

- Ядро: модульные тесты; эталон — 63 акта из книги инженера и его пример строки.
- Сканы: эталон — образец АОСР №ЗР/ВГ/1 с записанными ответами моделей (тест не ходит в сеть);
  отдельный ручной прогон на живых моделях. Нужны ещё 5–10 сканов от инженера.
- Агент: набор из 10–15 сценариев диалога на живой модели с проверкой, какие инструменты вызваны
  («удали акт …» → запрос подтверждения, «что за август» → поиск, без изменений реестра).
- Сквозная проверка в Telegram на тестовом боте перед тем, как отдавать инженеру.

## Порядок работ

0. **Проба pi с локальной моделью** (полдня, одноразовый код): сессия без встроенных инструментов,
   два своих инструмента, `qwen3.8-27b` через хаб, 5 реплик. Критерий: модель стабильно вызывает нужный
   инструмент с верными аргументами. Не проходит — пробуем другую модель хаба, затем запасной путь
   (свой цикл на Python). Решение принимает Алексей по результату.
1. Ядро: команды с JSON, история версий, операции правки/удаления/отмены, спорные места.
2. Разбор сканов.
3. Бот и агент.
4. Запуск в постоянную работу.

Этапы 1 и 2 не зависят от исхода пробы и планируются сразу. При запасном пути меняется только этап 3:
бот и цикл агента пишутся на Python (aiogram), Node из проекта уходит; команды ядра те же.

## Риски

- Локальная модель плохо вызывает инструменты в pi → этап 0 выявляет это до основной работы.
- Две модели ошиблись одинаково на скане → пометка «из скана» в отчёте, инженер сверяет выборочно.
- API pi изменится → версия зафиксирована.
- Два стека (Python + Node) → граница одна: команды ядра с JSON.

## Решения, принятые исполнителем (можно оспорить)

- Библиотека бота — grammY; бот и агент в одном процессе Node.
- Спорные места и история версий — файлы в рабочей папке, без базы данных.
- Даты в реестре пишутся текстом «19.02.2025г.», как в примере инженера.
- Модель диалога — `qwen3.8-27b`; модели для сканов — `qwen3.6-fp8` (основная) + `qwen3.8-27b`.
- Акт со спорными местами попадает в реестр сразу, вопрос остаётся открытым.
- Ручные исправления запоминаются и переживают повторную загрузку акта.
- Реестр, присланный инженером, заменяет текущий целиком после сверки номеров актов.
- Чужие строки в реестре сохраняются как есть.
- Файлы больше 20 МБ бот не принимает.
- Расхождение количества в примере инженера — ошибка примера (подтверждено им), эталон — акт.

### Уточнения по итогам этапов 0–2 (14.11.2026)

- Проба pi: годится. Модель диалога — `qwen3.6-fp8` (15/15), а не `qwen3.8-27b` (пустые ответы).
  Встроенные инструменты выключаются `noTools: "builtin"`, свои передаются `customTools`.
- Удалённый акт запоминается и при повторной загрузке не возвращается; есть команда `restore`.
- Правки, сделанные инженером в Excel в колонках D–K, при приёме его файла становятся ручными правками.
- Поиск по тексту идёт по основам слов и захватывает строки приложений.
- Модель со скана переписывает строки целиком, поля выделяет общий код.
- На одном скане прогоны моделей отличаются: основная модель однажды прочла код 3.2.1.5 как 3.2.1.4,
  вторая это поймала. Сверка двух моделей обязательна, одной модели доверять нельзя.
- Место освидетельствования для дорожных актов с пикетами (без «на участке») остаётся пустым —
  правило нужно спросить у инженера.

### Уточнения к этапам 3–4 (15.11.2026, согласуются вместе с планом бота)

Отступления от текста выше; причина — у каждого.

- **Отчёт о загрузке и вопросы пишет код бота, а не агент.** Агент получает тот же отчёт служебным
  сообщением и отвечать на него не обязан. Причина: числа и номера актов в отчёте не должны зависеть
  от модели, а кнопки всё равно рисует бот.
- **Имена инструментов — латиницей** (`find_acts`, `show_act`, `set_field`, `delete_act`,
  `restore_act`, `list_issues`, `resolve_issue`, `undo_last_change`, `registry_summary`,
  `send_registry`). Причина: хаб не принимает кириллицу в именах функций.
- **Отмена последнего изменения — тоже через кнопку**, с подписью того, что отменяется. Причина:
  отмену нельзя отменить.
- **Свой вариант ответа на вопрос** («напишу сам») принимает бот, минуя агента. Причина: значение
  должно попасть в реестр дословно.
- **Вопросы одного акта идут одним сообщением**, по ряду кнопок на вопрос (не только приложения).
- **Память разговора ограничена.** Когда сессия агента разрастается, бот начинает новую; реестр и
  открытые вопросы при этом не теряются. Сжатие истории pi не используется (с локальной моделью
  не проверено).
- **Все команды ядра идут через одну очередь** в боте — этим закрыт риск одновременных команд.
- Ядро дополняется командой `inspect` (реестр это, книга актов или скан) и полем `last_change`
  в `summary`.
- Бот работает на маке под launchd (предложение из раздела ниже, принято как рабочее допущение);
  токен бота хранится в связке ключей macOS.
